# 1.0 Contract Matrix

Status: Accepted for 1.0 Release Candidates
Owner: 0disoft

## Classifications

- `stable`: consumers may depend on the named behavior throughout 1.x. A breaking change requires a
  2.0 release unless a compatible deprecation path preserves existing callers.
- `experimental`: usable and tested, but the named extension may evolve in 1.x. Experimental data
  never changes the stable core fields around it.
- `internal`: implementation detail. Consumers must not parse, generate, or depend on it.

## Package And Runtime

| Surface | Classification | Compatibility promise |
| --- | --- | --- |
| npm package `@0disoft/service-catalog-generator` | stable | Package identity remains public. |
| executable `scg` | stable | Installed package exposes this binary. |
| Node.js 24 minimum runtime | stable | Raising the runtime floor is breaking. |
| private workspace packages `@scg/*` | internal | They are not published or supported as consumer imports. |

## Manifest, Config, And Catalog

| Surface | Classification | Compatibility promise |
| --- | --- | --- |
| `scg.service/v1` | stable | Strict manifest input. Existing fields, accepted values, and defaults remain compatible in 1.x. |
| `scg.service/v1alpha1` input alias | stable compatibility alias | Accepted and normalized to `scg.service/v1` throughout 1.x; removal requires 2.0. |
| `scg.config/v1` | stable | Strict config input. Unknown keys continue to fail validation. |
| `scg.config/v1alpha1` input alias | stable compatibility alias | Accepted and normalized to `scg.config/v1` throughout 1.x; removal requires 2.0. |
| `scg.catalog/v1` | stable | Complete JSON snapshot and JSON report output. Additive optional fields are compatible; removal, narrowing, or meaning changes are breaking. |
| `scg.catalog/v1alpha1` output | retired pre-1.0 output | 1.0 release candidates emit `scg.catalog/v1`; regenerate snapshots instead of editing generated files. |
| `limits.*` keys and defaults | stable | Current defaults are compatibility floors. A 1.x release may raise a limit but must not lower it. Explicit user limits remain authoritative. |
| `validation.minimumServiceCount` | stable | Defaults to zero; positive values require that many valid, uniquely identified normalized services. |
| `sources[]` adapter ownership | stable | Roots are explicit, workspace-contained, disjoint after realpath resolution, and never schema-autodetected. |
| explicit `scg-v1` input selection | stable | Native schema remains the default and is never selected by autodetection. |
| explicit `zdp-v2` adapter | experimental | Selection remains explicit. Stable catalog fields keep their meanings; `extensions.zdp` may gain or refine fields. |
| `extensions.<namespace>` | experimental | Namespaces retain JSON values but are not interpreted as SCG policy. Stable core fields cannot be replaced by extensions. |

## CLI

| Surface | Classification | Compatibility promise |
| --- | --- | --- |
| commands `scan`, `check`, `report`, `completion` | stable | Names and command purposes remain available. |
| documented flags in `docs/cli/command-contract.md` | stable | Removal or semantic reversal requires a 2.0 boundary or compatible deprecation. |
| config precedence: flags, config, defaults | stable | Environment variables do not alter catalog policy. |
| exit codes 0 through 5 | stable | Meanings in `docs/cli/output-and-exit-codes.md` remain fixed. |
| diagnostic object fields | stable | `severity`, `code`, and `message` remain; optional location and hint fields keep their meanings. |
| documented diagnostic codes | stable | Codes are not renamed or repurposed in 1.x. |
| full `--json` snapshot | stable | Follows `scg.catalog/v1`. |
| bounded `--summary-json` payload | stable | Existing keys and meanings remain; additive keys are compatible. |
| human-readable wording and ordering | internal | Consumers must use JSON and diagnostic codes instead of parsing prose. |

## Reports

| Surface | Classification | Compatibility promise |
| --- | --- | --- |
| filenames `catalog.json`, `graph.dot`, `report.html` | stable | Selected formats use these names in the declared output directory. |
| complete-generation replacement | stable | Successful publication never mixes files from different SCG generations. |
| JSON report contents | stable | Follows `scg.catalog/v1`. |
| DOT and HTML presentation markup | experimental | Deterministic and escaped, but layout and labels may evolve. |
| `.scg-generation.json` contents | internal | Ownership marker only; consumers must not parse its schema or generation id. |
| `.scg-*` lock, stage, and backup names | internal | Recovery implementation detail with no naming compatibility promise. |

## GitHub Action And Release Channels

| Surface | Classification | Compatibility promise |
| --- | --- | --- |
| root `action.yml` | stable | Documented inputs, outputs, exit propagation, and Node.js 24 runtime remain compatible in 1.x. |
| exact prerelease tag such as `v1.0.0-rc.1` | stable release channel | Release candidates are consumed only through their exact tag. |
| moving major tag `v1` | stable release channel | Created or moved only by a stable 1.x release after release smoke passes. It never points to a prerelease. |
| moving major tag `v0` | frozen compatibility channel | Remains on the final 0.x release and is not moved by 1.x releases. |
| npm dist-tag `next` | prerelease channel | Points to the published release candidate. |
| npm dist-tag `latest` | stable channel | Never points to a prerelease. |
| committed `dist/action/index.cjs` implementation | internal | Generated executable release material, not an import or source API. |

## Release-Candidate Evidence

Before promoting a stable 1.0 release:

- run legacy-alpha and canonical-v1 fixtures through source, packed-package, and exact-version
  registry validation;
- run native and mixed consumers through the exact prerelease Action tag on Ubuntu and Windows;
- confirm npm `next` points to the release candidate and npm `latest` does not;
- confirm `v1` was not created or moved by the prerelease and `v0` stayed frozen;
- verify that no stable diagnostic code, exit code, report filename, Action input, or Action output
  changed without a migration entry.
