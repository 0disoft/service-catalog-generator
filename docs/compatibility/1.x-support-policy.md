# 1.x Support And Deprecation Policy

Status: Accepted
Owner: 0disoft

## Supported Line

The actively supported release is the latest stable `1.x` version on npm `latest`, together with
the current `main` branch. Older `1.x` patches remain installable and immutable but do not receive
routine backports unless a security advisory explicitly names an affected historical version.
Versions before 1.0 are unsupported; the Action `v0` tag remains frozen only as a compatibility
reference.

No 1.x end-of-support date is scheduled. Adding a sunset date, changing the supported line, or
raising the Node.js 24 runtime floor requires a reviewed update to this policy, `SECURITY.md`, the
compatibility matrix, and release documentation before the change takes effect.

## Release Types

- Patch releases contain compatible defect fixes, security fixes, documentation corrections,
  dependency maintenance, and internal build or CI changes.
- Minor releases may add optional commands, flags, fields, adapters, reports, or Action inputs while
  preserving every stable 1.x contract and default.
- Major releases may remove or narrow stable contracts only with migration documentation and an
  explicit 2.0 compatibility decision.
- Prereleases use exact npm versions and Action tags through npm `next`; they never move npm
  `latest` or Action `v1`.

## Stable Contract Rules

The surfaces classified as stable in `docs/compatibility/1.0-contract-matrix.md` remain compatible
throughout 1.x. In particular:

- `scg.service/v1alpha1` and `scg.config/v1alpha1` input aliases remain accepted through 1.x;
- existing fields, accepted values, CLI flags, JSON fields, diagnostic meanings, exit codes, report
  filenames, Action inputs, and Action outputs are not removed, renamed, or narrowed;
- resource defaults may become more permissive but not more restrictive;
- a new diagnostic may cover newly invalid or unsafe input, but a previously clean valid input must
  not start failing under `--fail-on-warning` without an opt-in compatibility path or a major
  release;
- human wording and internal recovery metadata may improve without a compatibility promise.

## Deprecation Process

Deprecation starts with a changelog entry, replacement guidance, and a migration example. During
1.x, deprecated stable input remains functional and canonical output remains unchanged. A future
2.0 release may remove it only after the migration guide and exact-version consumer conformance
cover both the old and replacement paths.

Deprecation notices must not silently turn a previously successful invocation into a nonzero exit
when `--fail-on-warning` is enabled. Documentation and release notes are the default notification
path; runtime diagnostics require a compatible opt-in or an existing invalid-input condition.

## Security And Forward Fixes

Security fixes target `main` and the latest stable 1.x line. Published npm versions and immutable
Git tags are never rewritten. If a release is affected, publish a forward-fix patch, move npm
`latest` and Action `v1` only after release smoke passes, and describe any exceptional historical
backport in the advisory.

Every supported release must pass the local `check`, byte-reproducible package smoke, external
consumer conformance, hosted CI and CodeQL, exact-version registry smoke, provenance, signature,
GitHub Release, and immutable/moving-tag evidence appropriate to that release.
